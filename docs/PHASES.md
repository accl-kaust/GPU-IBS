# GPU-IBS: implementation phases and measurements

This is the engineering log of the phased GPU acceleration of [FastIBS](https://github.com/githubcbrc/FastIBS) (design: *Accelerating FastIBS on GPUs: A Phased Implementation Design and Evaluation Plan*). It is kept in the order the work happened, so early result paragraphs quote numbers that later phases superseded; each such paragraph carries a note. For installation and usage see the [README](../README.md).

**Phase 0 — CPU baseline modernization (implemented):**

- `src/KmerCodec.hpp`: rolling 2-bit codec producing the canonical 64-bit packed k-mer per position in O(1), replacing the allocation-heavy string k-mer extraction (`substr` + `reverseComplement` + lexicographic min).
- `CKmerAPI::from_int` (thin addition to the vendored KMC API): builds the packed KMC query directly from the 64-bit code, eliminating the per-character `from_string` parse.
- Mapper coverage via a difference array + one prefix pass (O(N) instead of O(Nk) scattered increments), and linear-time serialization via `to_chars`.
- Streamed FASTA/FASTQ reading (no whole-file double-buffering) and 1 MB-buffered gzip decompression.
- The original string-based path is preserved as the correctness oracle and runtime-selectable via `FASTIBS_LEGACY=1` (CPU-BASE vs. CPU-OPT).

**Validation:** bit-exact TSV/mapping output vs. the unmodified code (k ∈ {25, 31}, contigs with lowercase bases, N runs, short windows); regression test in `tests/phase0_test.cpp`.

**Phase 1 — device-resident index and batched probe (implemented):**

- `src/gpu/KmcRaIndex.hpp`: loads the KMC random-access index directly from the on-disk `.kmc_pre`/`.kmc_suf` files (KMC1 and KMC2/0x200 formats, vendored API untouched), strips the interleaved counter bytes, and normalizes the big-endian-by-byte suffix records to native integers so a probe compares one word. KMC2's minimizer-signature bin selection (`signature_map` + `CMmer` norm table) is part of the probe structure and is replicated exactly — required for bit-exactness with `CKMCFile::CheckKmer`.
- `src/gpu/DeviceKmerIndex.cuh/.cu`: device-resident copy of the index (LUTs, signature map, norm table, counter-stripped suffixes) plus a grid-stride probe kernel (one query per thread, `__ldg` loads, single-integer suffix compares) mirroring the host probe operation for operation. Upload time and footprint are logged. `probe(d_queries, d_valid, n, d_hits, stream)` is the async primitive; `probeHost` is the synchronous staging wrapper used by the Phase 1 per-window path.
- `KmerDatabase.hpp`: batched GPU path in `getStatsFromSequence` — the window's codec output is probed on the device and the existing run-length statistics run over the returned bitvector unchanged. GPU is on by default when built with CUDA and a device is present; `FASTIBS_GPU=0` forces CPU.
- `src/CMakeLists.txt`: `-DFASTIBS_CUDA=ON` enables CUDA (sm_80 A100, sm_90 H100; sm_70 V100 was added to the default list later); binaries fall back to the CPU path at runtime without a device. Also builds `probe_bench`, the Phase 1 microbenchmark (probe throughput vs. a GUPS-style random-access ceiling).

**Phase 2 — fused, streamed end-to-end pipeline (implemented):**

- `src/gpu/ProbeCore.hpp`: the KMC membership probe written once as a host/device template — the host oracle (validated bit-exactly against `CKMCFile`), the Phase 1 kernel, and the Phase 2 fused kernel all call the same code, so the search logic cannot drift.
- `src/gpu/EncodeProbeCore.hpp`: the fused K1+K2 body, also host/device-shared: batch layout (word-aligned per-window regions), host 2-bit packing with a non-ACGT exception bitmask ("ship sequence, not k-mers": W/4 bytes up instead of 8(W−k+1)), rolling encode + canonicalization + immediate probe over 32 positions per thread (each thread exclusively owns one hit word and one validity word — no atomics), and the statistics pass over the returned bit masks.
- `src/gpu/EncodeProbe.cuh/.cu`: the streaming engine — a ring of `--streams` slots (default 3), each with pinned staging buffers, device batch buffers, a CUDA stream and an event; H2D, fused kernel and D2H of consecutive batches overlap across slots.
- `KmerDatabase.hpp`: `processReference` batches windows (~`--batch-mb` MB of sequence, default 128), packs them on the thread pool, streams them through the engine, and hands each completed batch's statistics back to the pool — the pool keeps its job (packing + statistics) and the code keeps its shape. The device index uploads lazily on first use, so the mapper/intersect tools never pay for it.
- `FastIBS.cpp`: `--gpu/--cpu`, `--batch-mb=N`, `--streams=N`, `--sync` (the Phase 1 per-window path, kept as an ablation/debug configuration).
- Host memory: windows are now `string_view`s over the contigs (no per-window copies), removing the former 2× host-memory overhead on large references.

**Validation:** `tests/phase2_test.cpp` drives the exact shared kernel-body templates through packing, layout, and stats on the host, against the Phase 0 codec reference — synthetic predicates at k ∈ {25, 31, 32} across window shapes (lowercase, N runs, tails, windows of exactly k and k−1 bases), capacity-sweep batch splitting, plus a real database with hit-heavy windows. The streamed binary's TSV output is bit-exact vs legacy in CPU-fallback mode; `scripts/slurm_phase2.sbatch` is the on-GPU gate (bit-exactness vs CPU and vs `--sync`, timing sweep, optional Nsight overlap capture).

**Phase 2 gate results (A100-SXM4-40GB, 2×10⁹-k-mer database, 2 Gbp reference, window 50 kb):** all configurations bit-exact; whole-binary wall time CPU-OPT 130.0 s vs GPU-sync 25.6 s vs **GPU-streamed 21.4 s — 6.1× end-to-end**. *Superseded* once the on-disk index repack was parallelized (job 58667, same node and gate): CPU-OPT 130.8 s vs GPU-sync 14.6 s vs **GPU-streamed 11.0 s — 11.9×** (11.4× on an A100-80GB-PCIe node). GPU time is flat across window sizes (21.4–22.1 s for w ∈ {10⁴, 10⁵, 10⁶}) while CPU-OPT stays ~129 s. The lazy RA open means GPU runs never load the 12 GB host copy of the suffix array (db-load: 0.03 s); the remaining GPU wall time is dominated by reading the on-disk index for the device copy, reading the 2 Gbp FASTA, and the streamed pipeline itself.

**Phase 3 — probe structures and query ordering, the paper's ablations (implemented):**

- **GPU-BS-SORTED** (`--sort-queries`): a CUB radix sort of each batch by k-mer value (position payload) between encode and probe, converting the random access pattern into a quasi-sequential sweep of the suffix array — coalesced LUT reads and L2-resident upper search levels, at the cost of ~2× extra device traffic. Invalid/padding positions carry an all-ones sentinel (a canonical code can never be all ones) and sort to the end.
- **GPU-HASH** (`--probe=hash`, `--hash-lf=F`): an open-addressing hash set of full canonical codes (double hashing, host/device-shared in `src/gpu/HashCore.hpp`), built once per database on the device from the ported index's own records (`KmcRaIndex::forEachKmer` — no KMC rebuild, no listing pass) with build time and footprint logged. O(1) expected probes vs the index's O(log) chain, at ~8/lf bytes per k-mer vs the index's ⌈2(k−p)/8⌉.
- **Pinned LUT** (`--pin-lut`): an L2 persisting access-policy window over the prefix LUT, measuring whether the two LUT loads per query matter at all.
- `probe_bench` gained the same axes (`--sorted`, `--hash`, `--hash-lf=F`, `--pin-lut`) and reports each mode's throughput against the GUPS ceiling; `scripts/slurm_phase3.sbatch` fills the whole matrix — {BS, BS+pinned, BS-SORTED, HASH×3 load factors} — and requires every configuration's TSV output to stay bit-identical.

**Validation:** `tests/phase3_test.cpp` — the enumerated k-mer set equals a full KMC listing pass; the hash backend agrees with the ported-index probe on every present k-mer and 500k random queries at three load factors; the sorted path's hit/valid words are bit-identical to the fused path's. All of it exercises the same host/device-shared templates the kernels instantiate.

**Phase 3 gate results (A100-SXM4-40GB, 2×10⁹-k-mer database, all configurations bit-exact):**

| configuration | probe throughput | footprint | build/upload |
|---|---|---|---|
| GPU-BS | 1.33 Gq/s | 15.3 GB | 0.77 s upload |
| GPU-BS + pinned LUT | 1.39 Gq/s (+4%) | 15.3 GB | — |
| GPU-BS-SORTED | 1.97 Gq/s (1.49×) | + sort buffers | sort timed one-shot: 1.8–6.1 ms across jobs (not a kernel time; being re-measured) |
| GPU-HASH lf=0.5 | 6.49 Gq/s (4.89×) | 30.5 GB | 4.8 s build |
| GPU-HASH lf=0.6 | 5.22 Gq/s (3.94×) | 25.4 GB | 4.9 s build |
| GPU-HASH lf=0.8 | 2.65 Gq/s (2.00×) | 19.1 GB | 4.8 s build |

End-to-end, the probe structure does not help (with the serial repack: GPU-BS 23.0 s, BS-SORTED 22.9 s, HASH 25.5 s including its build; with the parallel repack, job 59626: GPU-BS 11.3 s, pinned −1.3%, sorted +1.7%, HASH +26%): after Phase 2 about half of the scan is host-side loading, and the hash's ~5 s build exceeds what its faster probes can save. The ablation therefore argues for GPU-BS as the production default — zero build cost, smallest footprint, same output — while HASH's 4.9× probe throughput matters where probing dominates (e.g. the all-pairs intersection workload of Phase 4). The pinned-LUT axis is muted on these databases because KMC chose p=5 (a 4 MB LUT that is L2-resident anyway); production-scale LUTs (p=12–13) are the interesting regime.

**Phase 4 — Mapper, KDBIntersect, multi-GPU (implemented):**

- **Mapper**: `fastibsmapper` now runs on the streamed pipeline. Contigs are chunked position-partitioned (k−1 base overlap, every k-mer position in exactly one chunk); each hit adds ±1 to the contig's difference array (atomically at chunk seams) and one prefix pass materializes the coverage track through the same serializer the CPU path uses — byte-identical output by construction. Controlled by the same env switches (`FASTIBS_GPU=0` forces CPU).
- **KDBIntersect**: the larger database becomes the device-resident index; the smaller one's k-mers are enumerated straight from its on-disk index (`forEachKmer`, no KMC listing pass) and probed in 32M batches, with only per-batch counts returning (`probeCountHost`, device-side reduction). This is the workload where the Phase 3 probe-throughput numbers translate directly — the all-pairs matrix use case.
- **Multi-GPU** (`--gpus=N`): each device holds a full index replica and its own ring of pipeline slots; consecutive batches round-robin across devices. Shards are independent — no peer copies. Output is identical to single-GPU by construction (per-window results land by global window index). *Superseded by Phase 5 below: the index is now split across the devices, not replicated.*
- **Out-of-core** (databases exceeding device memory) is deferred to future work; the sizing model shows the target databases fit an 80 GB part when KMC writes them at a prefix length p ≤ 7 (a 10¹⁰-k-mer index is 80 GB of suffix area; p = 11 adds 17 GB of look-up tables), and multi-GPU replicas cover the matrix workload.

**Validation:** `tests/phase4_test.cpp` — the mapper chunker provably partitions positions (checked at several chunk sizes including pathological ones); pipeline coverage strings are byte-identical to the CPU reference on synthetic (lowercase/N-run/short/exact-k) and real-database contigs; intersection via enumeration equals intersection via KMC listing. `scripts/slurm_phase4.sbatch` is the on-GPU gate: mapper byte-exactness, intersection GPU==CPU, and the `--gpus=1..N` strong-scaling sweep with identical outputs.

**Phase 4 gate results (A100, 2×10⁹-k-mer database, 2 Gbp reference):**

- **Mapper: GPU 45.4 s vs CPU-OPT 166.1 s — 3.7×, byte-identical** (single- and dual-GPU; job 58664, both paths on a warm page cache, parallel repack). An earlier figure of 32.5× against a 1864.9 s baseline was *withdrawn*: that CPU mapper parallelized only across contigs and ran single-core on a single-contig reference. Phase breakdown: probe 122.8 → 5.1 s (24×); serializing and writing the one-integer-per-base coverage track (~32 s) is shared by both paths and is now 70% of the GPU's wall time.
- **Intersection**: GPU == CPU exactly — self-intersection of the full 2×10⁹-k-mer database (2,000,199,169) and cross-intersections both match.
- **Multi-GPU on one reference is flat** (after the parallel repack: 11.6 → 11.2 s on the 40 GB node and 11.4 → 12.8 s on the PCIe node from 1→2 GPUs; 21.8 → 22.6 s before it): expected and honest — the device is at most half of a single-reference scan, so adding devices adds only replica-upload cost. Multi-GPU capacity pays off where the device is the bottleneck: the all-pairs intersection matrix (one process per GPU via `CUDA_VISIBLE_DEVICES`), probe-bound configurations, and concurrent multi-reference runs. *(Measured with the replicated design; the split design of Phase 5 changes what a second device costs and buys — see below.)*

**Phase 5 — the index split across devices (implemented; on-GPU gate PASSED on 2×V100, job 68742, and 2×A100, job 68756):**

Phase 4 replicated the whole index on every device and round-robined batches across the replicas: no per-device memory saving, and — the device being at most half of a scan's wall time — no speedup either, only the extra replica upload. Phase 5 replaces replication with **sharding**: with N devices, device d holds ~1/N of the index and searches only its own k-mers. One device still holds the whole index, uploaded verbatim, so the single-GPU structure and its measurements are unchanged.

- **Shard = a prefix range of every signature bin** (`KmcRaIndex::shardPlan` / `shardLayout`). The 4^p prefix buckets are cut into N contiguous ranges of ~equal *record* counts (canonical k-mers are skewed towards small prefixes — canonical = min of the two strands — so the cut is cumulative, not an equal split of the prefix space; balance is within one bucket's share). Within a bin the records are sorted by prefix, so a shard's records are one contiguous run per bin, gathered bin after bin into one device array (one `cudaMemcpy` per bin, straight from the host arrays); its LUT is the per-bin entries of the range, rebased onto the gathered array with a stride of `prefixHi−prefixLo+1` entries per bin. The single shard covering every prefix has the on-disk stride and reproduces the on-disk arrays exactly (checked by the test). `fastibs::ProbeParams` carries the prefix range; `probeOne` rejects a query outside it *before* the signature scan, so a device answers another shard's query for the cost of the encode alone. Each k-mer is held by exactly one shard, so the OR of the shards' answers is the whole index's — bit-exactness by construction, for any N.
- **Hash backend**: shard d holds the keys with `hashShardOf(key, N) == d` (a salted mix independent of the slot and step hashes), in a table sized for its share (mean + 8σ; the insert kernel bounds its walk and fails loudly rather than spinning if that were ever exceeded); `hashContains` rejects other shards' keys first. The shards' key counts are checked to sum to the database's.
- **Pipeline** (`EncodeProbeEngine` is one engine over all devices). A batch goes to **one** device, its *encoder*, chosen round-robin so every device encodes 1/N of the batches. The encoder runs K1 over the whole batch, tallies each valid position's owner from its canonical code (prefix range for the ported index, owner hash for the hash backend), and partitions the (code, position) pairs into one contiguous segment per shard (block-local counts, one cursor reservation per shard per block, scatter). The other devices' probe kernels read their segment straight out of the encoder's memory and write one hit flag per query back into it — NVLink where present, PCIe peer-to-peer otherwise (`cudaDeviceEnablePeerAccess` on every pair; the topology is logged at startup). If some pair has no peer access, the engine stages the partition and the flags through host memory with `cudaMemcpyPeerAsync` instead (one code path, different pointers). Stream/event dependencies chain encoder → owners → encoder (`cudaStreamWaitEvent` across devices); the encoder scatters the flags into the position-indexed hit mask and returns hit + validity masks over the link the batch came in on. The host side is therefore the single-GPU pipeline — one hit mask per batch, no merge, no routing decision on the host. Per device: encode(1/N of the batches) + probe(1/N of the queries); peer traffic 8 B out + 1 B back per routed query, (N−1)/N of the queries. Routing buffers: 20+N bytes per position of batch per slot on each device (codes, partitioned codes + positions, flags; +9 B in staged mode). `--sort-queries` stays a single-device option.
  *This replaced an earlier Phase 5 draft that broadcast every batch to every device and had each device encode the whole batch, probe its own k-mers and return a partial mask for the host to OR — simpler, but it duplicated the encode and the PCIe upload N times; the PI's design routes on the device instead.*
- **Uploads** run concurrently, one host thread per device (`DeviceKmerIndex::buildShards`, `DeviceHashIndex::buildShards`), each moving 1/N of the index; a pre-flight check compares the shard size with each device's free memory and names the knob when it will not fit.
- **KDBIntersect** routes the enumerated k-mers on the host to the shard holding their prefix (the same test the device applies), so every query crosses PCIe once and each device searches only its own; per-device chunks (32M/N keys) are probed on helper threads while the enumeration keeps filling the next. Per-shard counts sum to the intersection because each k-mer is held by one shard. The tool follows `FASTIBS_GPUS` (it has no options).
- **`--sync`** routes each window's codes on the host to the shard holding their prefix and scatters the answers back by index (the codes are already on the host in that path).
- **CLI**: `--gpus=N|all` — default now *all visible devices* (or `FASTIBS_GPUS=N`), since with the split each additional device lowers per-device memory instead of adding a replica; `CUDA_VISIBLE_DEVICES` selects which devices, and one-process-per-GPU packing works as before.

**Validation:** `tests/phase4_test.cpp` gained the sharding checks, CPU-only through the shared templates: for N ∈ {1, 2, 3, 5} the plan partitions the prefix space with record counts summing to the total; N = 1 reproduces the on-disk LUT and suffix array verbatim; every present k-mer probes true on exactly one shard's gathered image and that shard is the plan's owner of its prefix; 200k random queries agree with the whole-index probe with never more than one shard hitting; the same partition/uniqueness/agreement checks for hash shards. `scripts/slurm_phase4.sbatch` keeps the multi-GPU byte-identity gate (mapper and `--gpus=1..N` scan, now checking that the index was actually split) and the strong-scaling sweep, which from now on measures split — not replicated — devices; the intersection check requires one "index shard i/N resident" line per device. **No multi-GPU timings of the split design have been recorded yet**.

**Gate (2026-09-22, jobs 68739–68743, mcnode32/mcnode37, 2×Tesla V100-SXM2-16GB over NVLink):** the first on-GPU run FAILED — single device bit-exact and the sharded intersection equal, but `--gpus=2` lost hits nondeterministically (2 of 51 rows differed, differently on each run; `--gpus=2 --sync`, the host-routed path, was exact). Cause: `submitRouted` never pre-set the flat code array to the sentinel; `encodeWord` emits only the positions inside each window, so the padding entries at the tail of a window's last output word kept stale or uninitialized codes, and `partitionKernel` took them for queries, overran their owner's segment and overwrote the next owner's real queries. The single-device sorted path had the memset, the routed path did not. Fixed with one `cudaMemsetAsync(d_codes, 0xFF)` before the route kernel; job 68742 then PASSED (mapper and scan byte-identical with the index split, intersection counts equal), and job 68743 confirmed all two-GPU configurations (default, repeat, `--sync`, `--probe=hash`, `--streams=1`, `--batch-mb=1`) at 0 differing rows and the mapper at 0 differing bytes. At scale (`corpus_big`, 2×10⁹ k-mers, 16 GB image) a second defect surfaced (job 68747): the routed pipeline's buffers — ~21 B per batch position per slot, 9.85 GB per device at 128 MB × 3 streams — did not fit beside the 7.6 GB shard on a 16 GB V100, the engine's constructor threw, and the driver (as in the original FastIBS) only wrote the error to `log.txt` and exited 0 with no output file. Fixed by sizing the batch to the memory left beside the shard (`EncodeProbeEngine::estimateDeviceBytes`, halving from the requested `--batch-mb` down to the largest window, with a `[gpu] pipeline buffers:` line) and by having both drivers report a failed reference on stderr and exit 1. Job 68751 then reproduced the CPU output byte for byte with one and with two V100s (scan and mapper), 2 shards 1.42× faster than the whole index on one device. The same gate PASSED on the paper's platform, 2×A100-SXM4-40GB (mcnode25, job 68756), and on four A100s of that node under the `spot` QOS (job 68785: `--gpus=1/2/3/4` identical, mapper four-way split byte-identical), and job 68757 gave the first split-design numbers at `corpus_big` scale there: 9.87 s on one A100, 9.29 s on two shards, 128.83 s CPU-OPT on 16 cores, all byte-identical (mapper 59.7 vs 58.6 s, identical 5.7 GB output) — a single reference stays host-bound, two devices buy capacity, not speed. On three V100s (mcnode34, jobs 68782/68783) the gate passed with `--gpus=1/2/3` identical, and at `corpus_big` scale one, two and three shards gave byte-identical output (24.3 / 16.9 / 15.9 s processing; three-shard intersection and mapper identical too). Four devices exist only on the A100 nodes, where the normal QOS allows two per user. Single runs; the paper's 1→2 GPU rows still show the replicated design.

**Phase 6 — panel mode: one reference pass, N databases (implemented; on-GPU gate PASSED on 2×A100-80GB, Ibex job 54696020):**

Once probing runs on the device it is a fifth of a scan and the host sets the pace (bench, job 68921), while the real workload is a panel of many samples against one reference. Panel mode makes the reference-side host work a one-off. Design, memory budget and cost model: [`docs/MULTIDB_SCAN.md`](MULTIDB_SCAN.md).

- **CLI** (`fastibs` only): `--db=<folder>` (repeatable), `--db-list=<file>`, `--resident=N`. Without them every code path and log line of a single run is unchanged.
- **Host** (`src/KmerPanel.hpp`): the reference is read and windowed once per reference (`KmerDatabase::readReferenceWindows`, now shared with the single scan, as is the TSV writer). Databases are taken in rounds that fit the device(s) beside the pipeline buffers, planned from the KMC headers and `.kmc_pre` sizes. A single round stays resident across references; otherwise rounds are released before the next is uploaded.
- **Device**: one encode, N probes. `encodeProbeWordMulti` (shared host/device, `EncodeProbeCore.hpp`) runs the rolling encode once per position and probes every resident database, with the minimizer signature computed once per k-mer when the databases share k and the signature length (`probeOneWithSig`, `ProbeCore.hpp`). Slots carry one hit mask per database and one validity mask. With several devices, every database of a round is split with one joint cut (`KmcRaIndex::jointShardPlan`, at the coarsest prefix length among them), so the device-side router is unchanged and each owner probes its segment against its shard of every database, n flags per query. Ported index and fused order only.
- **CPU**: per window, the codec runs once and each database's `IsKmer` loop runs over the same codes (`KmerDatabase::getStatsFromSequenceMulti`).

**Validation (WSL, CPU-only and CUDA-without-device builds, 2026-10-28):** `tests/phase6_test.cpp` passes on 5-database panel corpora at k = 25 and k = 31 (`scripts/make_test_panel.sh`). The multi-database body's hit words equal n single-database bodies on every output word for n ∈ {2, 3, 5}, with the signature shared and per database. `probeOneWithSig` agrees with `probeOne` on every k-mer. The joint cut puts every sampled k-mer of every database on exactly its owner's shard for 1, 2, 3 and 5 devices. `scripts/gate_multidb.sh` passes on both builds at both k: N ∈ {2, 3, 5}, W ∈ {10⁴, 5×10⁴}, one round and `--resident=2`, two references in one folder, 48 TSVs byte-identical to single runs per configuration. Single runs of the new build are byte-identical to HEAD's on all 20 corpus runs, and their logs differ only in timings. Phases 0–4 host tests pass. **On-GPU gate (Ibex job 54696020, gpu101-09-r, 2×A100-SXM4-80GB, 2026-10-28): PASSED.** `scripts/slurm_multidb_gate.sbatch` ran `gate_multidb.sh` with `--gpu --gpus=1` (the multi-database fused kernel), `--gpu --gpus=2` (routed kernels, every database split by one joint cut) and `--cpu`, at k = 25 and k = 31: 48 TSVs byte-identical to single runs in each of the six configurations. **Timing (Ibex job 54696030, one A100-SXM4-80GB, barley vs MorexV3, W = 50 000):** 11.3–12.1 s per sample as separate runs, 7.85 / 6.12 / 5.36 s in the panel at N = 2 / 4 / 8 (1.5× / 2.0× / 2.1×), all eight databases resident in one round, every output byte-identical; the cost model had predicted 7.9 / 6.8 / 6.3 s.

**Building with the GPU path:**

```bash
conda create -n gpuibs -c conda-forge -c bioconda cmake ninja boost-cpp zlib kmc -y
conda activate gpuibs
conda install -c conda-forge cuda-toolkit=12.4 -y   # provides nvcc; skip if a CUDA module is available
cmake -S src -B build -G Ninja -DFASTIBS_CUDA=ON -DCMAKE_PREFIX_PATH=$CONDA_PREFIX
ninja -C build
```

Omit `-DFASTIBS_CUDA=ON` for a CPU-only build. The CUDA build runs on machines without a GPU too — it reports `[gpu] no CUDA device found` and uses the CPU path.

**Test corpus and validation on a SLURM cluster:** `scripts/make_test_corpus.sh` generates a synthetic regression corpus (reference with lowercase bases, N runs of length 1/k-1/k/3k, a contig shorter than k, a contig exactly k long, plus a KMC database built from a mutated copy so hit/miss runs and variations are non-trivial). `scripts/slurm_phase1.sbatch` runs the Phase 1 gate on a GPU node — `probe_bench` throughput plus a GPU-vs-CPU bit-exact TSV diff:

```bash
bash scripts/make_test_corpus.sh $PWD/corpus 25
sbatch scripts/slurm_phase1.sbatch $PWD/corpus/db $PWD/corpus/refs 50000
```

**Validation:** `tests/phase1_test.cpp` verifies the directly-loaded index against `CKMCFile` on real databases — every present k-mer probes as a hit and millions of random/codec-derived queries agree exactly. The Phase 1 gate (`scripts/slurm_phase1.sbatch`) **passed on an A100-SXM4-40GB** (driver 535, CUDA 12.4): GPU TSV output bit-exact vs the CPU path, 3.1 Gq/s probe throughput at 68% of the measured GUPS random-access ceiling on a 2.2M-k-mer test corpus (22.8 MB index, 3.2 ms upload). Note the test index fits in the A100's L2 cache, so these are L2-regime numbers; the paper's DRAM-regime measurements need order-10⁹-k-mer databases.

**Later engineering (Sept 2026):** the on-disk index repack that every GPU run performs was parallelized (12–16 s single-threaded → 1.3–1.8 s on 16 threads), which is what moved the scan from 6.1× to 11.9× and the mapper from 2.8× to 3.7×; the loader sizes its threads from the process's CPU affinity mask and prints `[gpu] index read+repack: X s (N threads, G GB, B GB/s)` so a cold read from storage is recognizable; the SLURM gates warm the page cache before timing and print device-health lines (one nominally identical A100 node was found running at a fifth of the usual probe throughput and its job excluded).
